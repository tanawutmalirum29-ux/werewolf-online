เกม werewolf ออนไลน์

## ⚠️ กฎการตั้งชื่อไฟล์ deploy zip (ห้ามฝ่าฝืน)

ทุกครั้งที่แพ็กไฟล์ deploy zip ส่งให้ผู้ใช้ **ต้องตั้งชื่อไฟล์ว่า `werewolf-deploy.zip` เสมอ**
ห้ามใส่เลขต่อท้าย ห้ามเปลี่ยนชื่อเป็นอย่างอื่นเด็ดขาด แม้จะ deploy ซ้ำหลายรอบในการสนทนาเดียวกันก็ตาม
(ให้ลบ/เขียนทับไฟล์เดิมที่ path `/mnt/user-data/outputs/werewolf-deploy.zip` แทนการสร้างชื่อใหม่)

**ห้ามมีโฟลเดอร์ครอบอีกชั้นข้างในเด็ดขาด** — ตอนสร้าง zip ต้อง `cd` เข้าไปในโฟลเดอร์โปรเจกต์ก่อน
แล้วค่อย zip ไฟล์/โฟลเดอร์ลูกทั้งหมด (`server.js`, `public/`, `package.json`, ...) ตรงๆ ให้ไฟล์เหล่านี้
อยู่ที่ root ของ zip ทันทีที่แตกไฟล์ (เช่น `zip -r ../werewolf-deploy.zip .` จากในโฟลเดอร์โปรเจกต์)
ห้าม zip จากโฟลเดอร์แม่แบบ `zip -r werewolf-deploy.zip werewolf-app/` เพราะจะได้โฟลเดอร์ `werewolf-app/`
ครอบไฟล์ทั้งหมดไว้อีกชั้น ทำให้ deploy ไม่ตรง path ที่ระบบรันจริงต้องการ (คาดหวัง `server.js` ที่ root)

## ⚠️ เบรกพอยต์มือถือ/ไอแพด (ต้องอ่านทุกครั้งที่แก้ขนาด/responsive)


ทุกครั้งที่ต้องแก้ CSS ที่เกี่ยวกับขนาดจอ/จำนวนคอลัมน์กริด/responsive layout ใน `host.html`
**ห้ามเดาเบรกพอยต์เอง — ให้ใช้ค่าที่กำหนดไว้แล้วนี้เท่านั้น** (อ้างอิงจาก CSS viewport จริงของอุปกรณ์ที่ใช้ทดสอบจริง):

- **มือถือ**: `max-width: 480px`
  (อ้างอิงจาก OPPO A5x จอ 720x1604 กายภาพ, DPR≈2 → CSS viewport กว้าง ~360px กันไว้ให้ครอบคลุมมือถือทั่วไปด้วยเลยตั้งเพดานที่ 480px)
- **ไอแพด**: `min-width: 481px` ถึง `max-width: 1279px`
  (ครอบคลุมทั้ง iPad แนวตั้ง CSS viewport 820px และแนวนอน 1180px)

ตัวอย่างการใช้งานจริงในไฟล์ (`public/host.html`) ดูที่ `.players-grid` (บรรทัด ~727-742) เป็นต้นแบบ:

```css
@media (max-width: 480px){
    .players-grid{ grid-template-columns:repeat(2, 1fr); }
}
@media (min-width: 481px) and (max-width: 1279px){
    .players-grid{ grid-template-columns:repeat(5, 1fr); }
}
```

อีกจุดที่ใช้เบรกพอยต์ชุดนี้: `public/player.html` ที่ `#players` (กริดผู้เล่นฝั่งผู้เล่น) — มือถือ 5 กริดต่อแถว, ไอแพด 6 กริดต่อแถว:

```css
@media (max-width: 480px){
    #players{ grid-template-columns:repeat(5, 1fr); }
}
@media (min-width: 481px) and (max-width: 1279px){
    #players{ grid-template-columns:repeat(6, 1fr); }
}
```

องค์ประกอบอื่นที่ต้องแบ่งจอมือถือ/ไอแพด (เช่น กริดสถานะในโหมดดูอย่างง่าย `.srow-status`) ก็ใช้เบรกพอยต์ชุดนี้เหมือนกัน

กริดผู้เล่นของ "โหมดดูอย่างง่าย" (`.players-simple-list`) ฝั่งโฮสต์ ก็บังคับให้จำนวนคอลัมน์เท่ากับ "โหมดดูปกติ"
(`.players-grid`) ทุกเบรกพอยต์ทุกขนาดจอ: มือถือ 2 / ไอแพด 5 / ไอแพดแนวนอนหลังคอลัมน์ซ้ายยุบ (`.layout.role-hidden`) 8
**ถ้าจะแก้จำนวนคอลัมน์ของกริดผู้เล่นต่อไป ให้แก้ทั้งสองที่ (`.players-grid` และ `.players-simple-list`) พร้อมกันเสมอ
ให้เลขตรงกัน อย่าแก้แค่ที่เดียว**
**อย่าตั้งเบรกพอยต์ใหม่ตามใจ (เช่น 380px, 700px, 800px ฯลฯ) โดยไม่ได้ตรวจสอบกับชุดนี้ก่อน**

### ข้อยกเว้น: `.players-grid` (ฝั่งโฮสต์) เป็น 8 คอลัมน์ เฉพาะไอแพดแนวนอน + หลังเริ่มเกม

หลังกดเริ่มเกม การ์ด "ตั้งค่าบทบาท" ในคอลัมน์ซ้าย (`#roleSettingsCard`) จะถูกซ่อน (`host.html` ~บรรทัด 3230-3234)
ทำให้คอลัมน์ซ้าย (`#leftCol`) ว่างเปล่าบนจอกว้างกว่า 980px (เช่นไอแพดแนวนอน 1180px) เพราะ `.layout`
ยังบังคับ `380px 1fr` เหมือนเดิม เลยติดคลาส `role-hidden` ที่ `.layout` คู่กันไปด้วย (toggle พร้อมกับ
`roleSettingsCard.hidden` ที่ `host.html` ~บรรทัด 3250) เพื่อยุบคอลัมน์ซ้ายและให้คอลัมน์ขวาขยายเต็มความกว้าง:

```css
.layout.role-hidden{ grid-template-columns:1fr; }
.layout.role-hidden #leftCol{ display:none; }
```

เมื่อคอลัมน์ขวาได้ความกว้างเต็มแล้ว **เฉพาะไอแพดแนวนอน** (`orientation:landscape`, ไม่ใช่แนวตั้ง) จึงขยาย
`.players-grid` จาก 5 เป็น 8 คอลัมน์ต่อแถวได้โดยการ์ดไม่แคบเกินไป — ก่อนเริ่มเกม (คอลัมน์ซ้ายยังอยู่) และ
ไอแพดแนวตั้ง (820px, เลย์เอาต์ยุบเป็น 1fr เต็มความกว้างอยู่แล้วตั้งแต่ ≤980px) ยังคง **5 คอลัมน์เหมือนเดิม**:

```css
@media (min-width: 481px) and (max-width: 1279px) and (orientation: landscape){
    .layout.role-hidden .players-grid{
        grid-template-columns:repeat(8, 1fr);
    }
}
```

**ถ้าจะแก้จำนวนคอลัมน์/เงื่อนไขนี้ต่อไป ให้เช็คกับส่วนนี้ก่อน อย่าเดาใหม่**

### ข้อยกเว้น: `public/player.html` เปลี่ยนเป็นเลย์เอาต์ 3 คอลัมน์ เฉพาะไอแพดแนวนอน (โชว์ทันทีที่เข้าห้อง ไม่ต้องรอเริ่มเกม)

เหมือนกับข้อยกเว้นของ `host.html` ด้านบน แต่ฝั่งผู้เล่น: เมื่ออยู่ในห้อง (คลาส `.app.game-visible` ติดตั้งแต่
ตอนเข้าห้อง/รอเริ่มเกม ไม่ต้องรอ `roomData.started`) ในเบรกพอยต์ไอแพดแนวนอน (`min-width:481px` ถึง
`max-width:1279px` + `orientation:landscape`) เท่านั้น จะสลับจากคอลัมน์เดียว (มือถือ/ไอแพดแนวตั้ง) เป็น
3 คอลัมน์: ซ้าย = แผงบทบาท (`#rolePopup`, กว้าง 270px), กลาง = กริดผู้เล่น (`#playersCard`), ขวา = แชท
(`#chatCard`, กว้าง 300px) — ทั้งสองแผงชิดขอบจอเต็มความสูง (`left:0`/`right:0` ตามฝั่ง)

- ใช้ `.app.game-visible` เป็นตัวคุมการแสดงผล (ไม่ใช่ `.app.game-started`) เพื่อให้เลย์เอาต์นี้โชว์ทันทีที่
  เข้าห้องเหมือนจอทั่วไป — `.game-started` ติดช้ากว่า (เฉพาะตอน `roomData.started` เป็นจริงจริง ๆ)
- `#rolePopup`/`#rolePopupOverlay` เป็น sibling ของ `.app` ที่ระดับ `<body>` (ไม่ใช่ลูก) จึงใช้ general
  sibling combinator (`.app.game-visible ~ #rolePopup`) แทน descendant selector — เดิมเป็นป๊อปอัปลอย
  กลางจอที่ต้องกดปุ่ม 🎭 (`#maskBtn`) ถึงจะเปิด ในเบรกพอยต์นี้ถูกบังคับ `display:flex !important` ให้
  ปักอยู่ซ้ายจอตลอดเวลาแทน (ไม่สนใจคลาส `hidden` ที่ `openRolePopup()`/`closeRolePopup()` ยังคงสลับอยู่)
  พร้อมซ่อน overlay/ปุ่มปิด (✕) เพราะไม่ใช่ popup แล้ว และซ่อนปุ่ม 🎭 กับข้อความชื่ออาชีพ/"แตะหน้ากากเพื่อดู
  รายละเอียด" (`#barRoleText`) ที่ `#bottomBar` เพราะไม่จำเป็นอีกต่อไป (ยังคงเหลือแค่ปุ่มความสามารถล้วนๆ)
- `#chatCard` เป็นลูกของ `.app` จริง ใช้ descendant selector ปกติได้ (`.app.game-visible #chatCard`) —
  ดึงออกจาก flex column เดิมของ `.app` มาปัก `position:fixed` ขวาจอแทน ทำให้ `#playersCard` ที่เหลืออยู่
  ใน `.app` (ซึ่ง `margin:0 auto` + `max-width:560px` อยู่แล้ว) กลายเป็นคอลัมน์กลางโดยอัตโนมัติ — ขอบล่างตั้ง
  `bottom:64px` แทน `0` เว้นที่ไว้ให้ `#bottomBar` ที่ย้ายมาปักอยู่ใต้แผงแชทแทน (ดูข้อถัดไป)
- `#bottomBar` (บาร์ใช้สกิล) เดิมลอยกึ่งกลางจอ (`left:50%` + `translateX(-50%)`, กว้าง `min(560px,100vw)`)
  ย้ายมาปักใต้แผงแชทแทน: `left:auto; right:0; width:300px` (เท่าความกว้าง `#chatCard`) +
  `justify-content:center` จัดปุ่มความสามารถให้กึ่งกลางแถบ — ตัดเฉพาะ `translateX(-50%)` ออกจาก
  transform (คง `translateY` ไว้เพราะใช้ร่วมกับอนิเมชั่นโชว์/ซ่อนบาร์ `.bar-visible`)

### ข้อยกเว้น: `public/player.html` ปักแผงบทบาทซ้ายจอ เฉพาะไอแพด**แนวตั้ง** (แชทอยู่ที่เดิม ไม่ย้าย)

ต่างจากไอแพดแนวนอนด้านบน (ที่กางเต็ม 3 คอลัมน์ ปักทั้งแผงบทบาทซ้ายและแชทขวา) เพราะจอแนวตั้งแคบกว่า
(CSS viewport 820px < แนวนอน 1180px ตาม breakpoint ที่กำหนดไว้ด้านบนสุดของไฟล์นี้) ไม่พอกาง 3 คอลัมน์เต็ม
รูปแบบให้อ่านง่ายเหมือนกัน เลยทำแค่ 2 ส่วน:

- ซ้าย = แผงบทบาท (`#rolePopup`) ปักอยู่ตลอด ชิดขอบเต็มความสูง เหมือนไอแพดแนวนอน แต่แคบกว่า
  (**220px** แทน 270px เพราะจอรวมแคบกว่า — เลข 220 มาจาก 220 + `.app` max-width เดิม 560px = 780px
  ยังพอดีกับจอแนวตั้ง 820px เหลือขอบ ~40px ถ้าจะแก้ความกว้างแผงต่อไป ให้เช็คเลขนี้ก่อน อย่าเดาใหม่)
- ขวา = เนื้อหาเดิมทั้งหมดของ `.app` (กริดผู้เล่น + แชท) **ไม่ได้แยกแชทออกไปปักขวาจอแบบแนวนอน** ยังคง
  ต่อท้ายกันแนวตั้งในลำดับ flex เดิมเหมือนโหมดมือถือทุกประการ (นี่คือสิ่งที่ผู้ใช้ระบุไว้ตอนขอแก้ฟีเจอร์นี้ —
  "แชทที่เดิม" เพราะจอเล็กกว่าแนวนอน) แค่ขยับพื้นที่ทั้งก้อนไปทางขวาอีกหน่อยเท่ากับความกว้างแผงบทบาท
  (`.app.game-visible{ margin-left:220px; margin-right:auto; }` แทน `margin:0 auto` เดิมที่ทำให้อยู่กลางจอ)
  เปิดที่ให้ไม่ทับกับแผงบทบาทซ้ายจอ
- `#bottomBar` (บาร์ใช้สกิล) เหมือนไอแพดแนวนอน ซ่อนปุ่ม 🎭 กับข้อความชื่ออาชีพ/"แตะหน้ากากเพื่อดูรายละเอียด"
  (`#barRoleText`) ออกเช่นกัน เพราะบทบาทโชว์อยู่แผงซ้ายจอตลอดเวลาแล้ว — เหลือแค่ปุ่มความสามารถล้วนๆ
  จัดกึ่งกลางแถบด้วย `justify-content:center` แทนเบียดชิดซ้ายหลังชื่ออาชีพหายไป **ไม่ได้ย้ายตำแหน่ง
  `#bottomBar`** (ยังคงกึ่งกลางเฉพาะพื้นที่ขวาแผงบทบาทเหมือนเดิม ต่างจากไอแพดแนวนอนที่ย้ายไปปักใต้แชทแทน)

ใช้เบรกพอยต์ไอแพดชุดเดียวกับด้านบน (`min-width:481px` ถึง `max-width:1279px`) + เฉพาะ
`orientation:portrait` เท่านั้น — ไม่กระทบมือถือ (≤480px) หรือไอแพดแนวนอนที่มีเลย์เอาต์ของตัวเองอยู่แล้ว

## สถิติผู้เล่น (อัตราชนะ) — ต้องตั้ง DynamoDB ก่อนใช้งาน

ป็อปอัปสถิติที่กดได้จากป้ายชื่อมุมขวาบนของหน้า Lobby (`public/index.html`) ดึงข้อมูลจาก DynamoDB
ผ่าน endpoint `/api/player-stats` (โค้ดฝั่ง server ดูคอมเมนต์เหนือ `STATS_TABLE_NAME` ใน `server.js`) —
เลือกใช้ DynamoDB แทนไฟล์ในเครื่อง/S3 เพราะรองรับการบวกสถิติแบบ atomic (`UpdateItem`) ไม่มีปัญหา
ข้อมูลชนกันหายแม้มีหลายห้องจบเกมพร้อมกัน หรือขยายเป็นหลาย EC2 instance ในอนาคต

**ต้องตั้งค่าครั้งเดียวก่อน deploy ถึงจะใช้งานได้** (ถ้ายังไม่ได้ตั้ง ป็อปอัปจะขึ้น "โหลดสถิติไม่สำเร็จ"
เฉย ๆ ไม่กระทบการเล่นเกมส่วนอื่น):

1. **สร้างตาราง DynamoDB** (DynamoDB Console → Create table)
   - Table name: `WerewolfPlayerStats` (หรือชื่ออื่นก็ได้ ถ้าเปลี่ยนต้องตั้ง env var `DYNAMODB_STATS_TABLE`
     ให้ตรงด้วย)
   - Partition key: `playerName` — String
   - Sort key: `statKey` — String
   - Table settings: เลือก **On-demand** (pay-per-request) ไม่ต้องตั้ง provisioned capacity
2. **ให้สิทธิ์ IAM** กับ instance role ของ Elastic Beanstalk environment (Role เดียวกับที่ตั้งไว้ให้สิทธิ์
   `elasticbeanstalk:DescribeEnvironments` อยู่แล้วสำหรับฟีเจอร์เช็คเวอร์ชัน) เพิ่ม policy ให้สิทธิ์
   `dynamodb:UpdateItem`, `dynamodb:PutItem`, `dynamodb:Query` และ `dynamodb:Scan` บน ARN ของตารางที่
   สร้างไว้ในข้อ 1 เช่น `arn:aws:dynamodb:ap-southeast-2:<account-id>:table/WerewolfPlayerStats`
   (`PutItem`/`Scan` ใหม่ล่าสุด — ใช้โดยฟีเจอร์ "ผู้เล่นทั้งหมด" ในหน้า admin ด้านล่าง)
3. **(ถ้าตั้งชื่อตารางอื่นไม่ใช่ค่า default)** ไปที่ Elastic Beanstalk Console → Environment →
   Configuration → Software → Environment properties เพิ่มตัวแปร `DYNAMODB_STATS_TABLE` เป็นชื่อตาราง
4. `npm install` (deploy pipeline ทำให้อัตโนมัติอยู่แล้ว) จะติดตั้ง dependency ใหม่
   `@aws-sdk/client-dynamodb` และ `@aws-sdk/lib-dynamodb` ให้เอง (อยู่ใน `package.json` แล้ว)

ไม่ต้องตั้ง region เอง — ใช้ `resolveRegion()` ตัวเดียวกับที่ระบบเช็คเวอร์ชันใช้อยู่แล้ว (อ่านจาก env var
`AWS_REGION` ก่อน ถ้าไม่มีจะถาม EC2 instance metadata เอาเอง)

**ข้อจำกัดที่รู้อยู่แล้ว:** สถิติผูกกับ "ชื่อที่ตั้ง" เป็น identity (ไม่มีระบบ account) — เปลี่ยนชื่อผ่าน
admin.html = เริ่มนับสถิติใหม่ภายใต้ชื่อนั้น ไม่ merge ของเก่าให้อัตโนมัติ

### กฎ "ออกเกม" — ผู้เล่นที่ออฟไลน์ตั้งแต่ 20% ของเวลาทั้งตาขึ้นไป ไม่นับแพ้/ชนะให้

ถ้าผู้เล่นกดย้อนกลับ/ปิดแอปทิ้งระหว่างเกมกำลังเล่นอยู่ (socket หลุดจริง) ระบบจะเริ่มนับเวลาออฟไลน์สะสม
ของคนนั้นทันที (ดูคอมเมนต์ `markPlayerOfflineStart`/`flushPlayerOfflineTime` เหนือ
`isPlayerCurrentlyConnected` ใน `server.js`) แยกจากสถานะ "🟡 กำลังเชื่อมต่อ.../⚫ ออฟไลน์" ที่โชว์ใน UI
(ซึ่งมีดีเลย์รอ 5-10 นาทีก่อนขึ้นสถานะ — ไม่เกี่ยวกับตัวเลขที่ใช้ตัดสินสถิติ)

ตอนจบเกม (`endGame` → `recordGameStats`) ถ้าเวลาออฟไลน์สะสมของคนนั้น **ตั้งแต่ 20% ขึ้นไป** ของเวลาที่เกมเล่น
ทั้งตาจนจบ (`room.startedAt` ถึงตอนจบเกม) จะถือว่า **"ออกเกม"** แทนแพ้/ชนะ — ไม่นับผลจริงให้เลยไม่ว่า
ทีมนั้นจะชนะหรือแพ้ (ดู `didLeaveGame`/`LEAVE_OFFLINE_RATIO` ใน `server.js`, แก้เกณฑ์ 20% ได้ที่ตัวแปรนี้)

**Schema เพิ่มคอลัมน์ `leaves`** (นอกจาก `games`/`wins` เดิม) ในแถว `TOTAL` และ `ROLE#<role>` — ไม่ต้อง
สร้างตารางใหม่หรือแก้ schema ด้วยมือ (`if_not_exists` จัดการให้อัตโนมัติ) ส่วน "แพ้" ไม่ได้เก็บเป็นคอลัมน์
แยก คำนวณย้อนกลับเสมอจาก `games - wins - leaves` (ดูฟังก์ชัน `rateBreakdown`) — ทั้งป็อปอัปสถิติหน้า
Lobby และหน้า admin (ประวัติรายคน) จะโชว์ "3 ช่อง" ชนะ/แพ้/ออก ทั้งจำนวนครั้งและ % เสมอ

**กฎการหนีออกเกมแบบกดหาห้องใหม่ (explicit):** ถ้าเกมรอบเดิมเริ่มแล้วและผู้เล่นกด **"หาห้องใหม่"** ระบบจะบันทึก `left=true` และ `leaveReason=new_room` ลงประวัติทันที ก่อนเปิดตัวเลือกห้องใหม่ และล็อก token ของผู้เล่นไม่ให้ย้อนกลับเข้ารอบเดิมนั้นอีก เกมใหม่/การเล่นรอบใหม่จะได้ `gameRoundId` ใหม่และไม่ติดธงหนีจากรอบก่อน

**การหลุดระหว่างเกม:** การกดย้อนกลับ/ปิดแอป/Socket หลุดจริงจะเริ่มสะสมเวลาออฟไลน์ทันที เมื่อจบเกม ถ้าเวลาออฟไลน์สะสมถึงเกณฑ์ 20% ของเวลาทั้งตา จะถูกนับเป็น `ออกเกม` และบันทึกในประวัติเป็นเหตุการณ์จบเกมที่ `left=true` แม้ไม่ได้กด "หาห้องใหม่" เอง

**สิ่งที่ไม่นับเป็นการหนี:** การออกจาก lobby ก่อนเกมเริ่ม, เกมที่จบไปแล้ว, และการปิดห้อง/บังคับปิดเซิร์ฟเวอร์แบบเงียบตามระบบดูแลเซิร์ฟเวอร์ ไม่เรียกสถิติแพ้/ชนะ/ออกของผู้เล่น


### หน้า admin — "ผู้เล่นทั้งหมด" (ทุกคนที่เคยตั้งชื่อ ไม่ใช่แค่คนที่กำลังเชื่อมต่ออยู่)

ใช้ตาราง DynamoDB เดียวกันด้านบน (ไม่ต้องตั้งตารางเพิ่ม) — แค่เพิ่ม statKey อีก 2 แบบ:
- `REG` — 1 แถวต่อ 1 ชื่อ เก็บ `firstSeen`/`lastSeen`/`joinCount` อัปเดตทุกครั้งที่มีคน "ตั้งชื่อเข้าห้อง
  ครั้งแรก" (ไม่นับตอน reconnect ด้วย token เดิม) หน้า admin ดึงรายชื่อทั้งหมดมาโชว์ + ค้นหาได้จากแถวนี้
- `EVENT#<เวลา>#<สุ่ม>` — 1 แถวต่อ 1 เหตุการณ์ (เข้าห้อง/จบเกม) ใช้ทำไทม์ไลน์ประวัติตอนกดดูรายคน

เข้าถึงได้จากหน้า `admin.html` เอง (แท็บ "ผู้เล่นทั้งหมด") ผ่าน endpoint ใหม่ 2 ตัว:
- `GET /api/admin/players?q=` — รายชื่อทั้งหมด (ค้นหาบางส่วนของชื่อได้ผ่าน `q`)
- `GET /api/admin/player-history?name=` — ประวัติของชื่อนั้น (สถิติรวม + ไทม์ไลน์เหตุการณ์)

**การยืนยันสิทธิ์:** endpoint กลุ่มนี้อยู่หลัง HttpOnly Admin Session ฝั่งเซิร์ฟเวอร์เสมอ — ต้องเข้าสู่ระบบแอดมินก่อน ไม่สามารถใช้แค่การรู้ URL หรือส่ง `auth.admin=true` เพื่อเรียกข้อมูลได้

## ความทนทานตอน Deploy / CloudFront 502-504

โปรเจกต์เพิ่ม `.ebextensions/01-high-availability.config` เพื่อให้ Elastic Beanstalk ใช้ **Immutable deployment**
และให้ Load Balancer ตรวจ readiness ที่ `GET /ready` แทนการใช้หน้าเกมเป็น health check. ตัวแอปจะไม่ถือการ
"ปิดเซิร์ฟเวอร์โดยแอดมิน" เป็น instance failure; `/health` เป็น liveness ที่ตอบได้เมื่อ process ยังมีชีวิต ส่วน `/ready`
เป็น gate จริงสำหรับรับ traffic และคืน 503 หาก bootstrap/room recovery ยังไม่พร้อม, process กำลัง drain หรือ Admin Auth ที่บังคับใน Elastic Beanstalk หายไป

ตอนรับ `SIGTERM`/`SIGINT` server จะเข้าสู่ draining state, หยุดรับ connection ใหม่, ปิด Socket.IO อย่างสุภาพ
และรอ HTTP connection ที่กำลังทำงานภายในเวลาที่กำหนดก่อนบังคับ exit เพื่อให้การถอด instance ใน deployment
ไม่ตัด connection แบบทันทีโดยไม่จำเป็น

### หน้า fallback ของ CloudFront

ไฟล์ `cloudfront-errors/server-unavailable.html` เป็นหน้า error แบบ standalone สำหรับอัปโหลดไป S3 **แยกจาก
Elastic Beanstalk origin** แล้วตั้ง CloudFront Custom Error Responses สำหรับ `502`, `503`, `504` ให้ชี้มายังไฟล์นี้
ดูขั้นตอนละเอียดใน `CLOUDFRONT-FAILOVER-SETUP.md`. หน้า fallback จะพยายาม reload แบบสุ่มช่วงเวลา เพื่อไม่ให้
ผู้เล่นทุกคนยิงกลับเข้า origin พร้อมกันทันทีที่ deployment เสร็จ

> ข้อสำคัญ: การเปลี่ยน source code อย่างเดียวไม่สามารถแก้ configuration ของ CloudFront distribution ที่มีอยู่จริงได้
> ดังนั้นการอัปโหลดไฟล์นี้และตั้ง Custom Error Response บน CloudFront เป็นขั้นตอน AWS ที่ต้องทำกับ distribution จริงแยกจาก
>การ deploy ZIP ของ Elastic Beanstalk

## รูปภาพเกมและไอคอนเว็บใช้ S3/CDN เท่านั้น

รูปภาพที่ผู้เล่นเห็นทั้งหมดต้องมาจาก S3 หรือ CloudFront ที่ชี้ไป S3 ไม่ใช่ไฟล์ใน deploy zip
ทั้งรูปอาชีพ/ตราสัญลักษณ์ และ site/profile assets (`favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`,
`apple-touch-icon.png`, `cover-1200x630.png`) ถูกแยกออกจากโปรเจคแล้ว

การตั้งค่า S3 เดิมยังใช้ตัวแปร `IMAGE_BASE_URL` เดียวกัน เพื่อให้ URL กลายเป็น `IMAGE_BASE_URL + /images/...`
และ site/profile assets ใช้ `IMAGE_BASE_URL + /favicon...` เป็นต้น

ตั้งค่า bucket/CloudFront ก่อน deploy:

1. สร้าง/ใช้ S3 bucket (เช่น `werewolf-online-assets`) แล้วอัปโหลดรูปอาชีพทั้งหมดไว้ใต้ `images/`
   เช่น `s3://werewolf-online-assets/images/xxx.jpg` และอัปโหลด site/profile assets 5 ไฟล์ไว้ที่ root ของ bucket:
   `favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`, `apple-touch-icon.png`, `cover-1200x630.png`
2. ให้ S3/CloudFront ที่ใช้เป็น image origin อ่าน object เหล่านี้ได้ตามวิธีที่คุณตั้งไว้
   (เช่น CloudFront OAC สำหรับ bucket private หรือ public-read ตามสถาปัตยกรรมที่ใช้งาน)
3. ไปที่ Elastic Beanstalk Console → Environment → Configuration → Software → Environment properties
   เพิ่มตัวแปร `IMAGE_BASE_URL` เป็น URL ของ bucket/CloudFront เช่น
   `https://<your-image-origin>` (ไม่ต้องมี `/images` ต่อท้าย และไม่ต้องมี `/` ปิดท้าย)
4. Apply แล้ว server จะเริ่มอ้างอิงรูปทั้งหมดจาก `IMAGE_BASE_URL + /images/xxx.jpg` และ
   site/profile assets จาก `IMAGE_BASE_URL + /favicon...` ทันที

จากนั้น deploy zip ไม่ต้องแนบ site/profile assets ทั้ง 5 ไฟล์อีกต่อไป และไม่ควรเพิ่มกลับเข้ามาใน `public/`
รูปทั้งหมดจะโหลดจาก S3/CDN โดยตรง

**สำคัญ:** `IMAGE_BASE_URL` ต้องถูกตั้งบน Elastic Beanstalk ให้เป็น S3/CloudFront URL ที่ใช้งานจริง
เพราะรุ่นนี้ไม่มี local-file fallback สำหรับรูปภาพแล้ว

การตรวจสอบรุ่นนี้ยังบล็อกการเข้าถึง `/images/*` จาก Elastic Beanstalk โดยตรง และ compatibility helper
ของหน้า host/player จะคืนค่าว่างแทนการกลับไปดึง `/images/...` เมื่อไม่มี S3/CDN base

**Site/profile assets 5 ไฟล์ที่ถูกแยกออก:** `favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`,
`apple-touch-icon.png`, `cover-1200x630.png`

## อัปเดต: ลดการใช้เน็ตของเกม (data-saving update)

ปรับให้เกมกินเน็ตของผู้เล่นน้อยลงที่สุดเท่าที่ทำได้ โดยไม่กระทบการเล่น:

1. **ตัด log แชทออกจาก `room_update`** — เดิม `wolfChatHistory`/`globalChatHistory` (ข้อความแชททั้งหมดที่ผ่านมาในเกม) ติดไปกับทุกครั้งที่มีการอัปเดตห้อง (โหวต, สลับโหมด, ฯลฯ) ทำให้ยิ่งเล่นนาน/แชทเยอะ ทุก action เล็ก ๆ ก็ยิ่งกินเน็ตมากขึ้นเรื่อย ๆ ตอนนี้ตัดออกแล้ว (ประวัติแชทยังส่งครบเหมือนเดิมตอน join/reconnect ผ่าน event แยก และข้อความใหม่ส่งทีละข้อความอยู่แล้ว) — นี่คือจุดที่กินเน็ตมากที่สุดในเกมเดิม
2. **เปิด gzip compression** (`compression` middleware) — บีบอัดหน้าเว็บ/ข้อมูล JSON ก่อนส่ง ทำให้ host.html/player.html (ไฟล์ละ ~120-140KB) เหลือขนาดเล็กลงมากตอนโหลดครั้งแรก
3. **เปิด WebSocket compression** (`perMessageDeflate`) — บีบอัดข้อมูลที่วิ่งผ่าน socket.io ระหว่างเล่น (room_update ฯลฯ)
4. **แคชรูปไอคอนอาชีพแบบ `immutable` 30 วัน** — โหลดรูปครั้งเดียวจริง ๆ ที่เหลือทั้งเกมใช้จาก cache เครื่อง ไม่ยิงเน็ตซ้ำอีกเลย (เดิม cache 7 วันแบบ revalidate ทุกครั้ง)
5. **ลดความถี่การเช็คเวอร์ชัน** จากทุก 30 วิ เป็นทุก 2 นาที (ยังเช็คทันทีทุกครั้งที่สลับกลับมาที่แท็บอยู่ดี ไม่กระทบการตรวจจับอัปเดตจริง)

**สิ่งที่ต้องทำก่อน deploy:** เพิ่ม dependency ใหม่ `compression` แล้ว (อยู่ใน `package.json`) ตัว deploy pipeline (เช่น Elastic Beanstalk) จะ `npm install` ให้เองตอน deploy ไม่ต้องทำอะไรเพิ่มเติม

   และห้องนั้น `room.started` แล้ว จะปฏิเสธด้วย `cb({ error: "started" })` แทนที่จะสร้างผู้เล่นใหม่ขึ้นมา
   เข้าร่วมกลางเกม — ผู้เล่นที่ reconnect ด้วย token เดิม (ตรงกับคนที่อยู่ในห้องอยู่แล้ว) ยังกลับเข้าห้อง
   ระหว่างเกมได้ตามปกติทุกประการ ไม่กระทบ flow นี้เลย
   - ฝั่ง client (`public/js/player.main.js`: `doJoin`) เช็ค `res.error === "started"` แล้วขึ้นข้อความ
     แจ้งเฉพาะเจาะจงว่า "ห้องนี้เริ่มเกมไปแล้ว เข้าร่วมใหม่ไม่ได้ระหว่างเกมกำลังเล่นอยู่" แทนข้อความกลางๆ
     "ไม่พบห้อง" เดิม
2. `host_add_bot` (`server.js`) — ปฏิเสธด้วย `cb({ error: "started" })` เช่นกันถ้า `room.started` แล้ว

     ทาง client อื่น (เช่นจอที่เรนเดอร์ค้าง)

## Running Version จาก AWS Elastic Beanstalk

`data.appVersion` ใช้ `utils/getAppVersion.js` เป็นแหล่งเดียวในการอ่าน `VersionLabel` ของ Elastic Beanstalk
ผ่าน `DescribeEnvironments`. ตั้ง `EB_ENVIRONMENT_NAME` และให้ instance role มีสิทธิ์
`elasticbeanstalk:DescribeEnvironments` เพื่อให้ได้ค่าเช่น `v3-57` ตรงกับ deployment ที่ environment กำลังรันอยู่จริง

`server.js` ไม่สร้าง Elastic Beanstalk client ซ้ำเองอีกแล้ว และ `/api/config` ใช้ค่า cached ที่มีอยู่เพื่อไม่ให้
การเรียก AWS control-plane ทำให้ endpoint เกมรอ; socket `serverInfo` ใช้แหล่งเดียวกันสำหรับป้าย Running Version
ในหน้าเกม

- `appVersion` มีหน้าที่แสดง **Running Version ของ deployment** เท่านั้น; ถ้าอ่าน AWS ไม่ได้จะเป็น `unknown`/`local-dev`
  โดยไม่ทำให้ `/api/config` ค้าง
- การตัดสินว่า "มีไฟล์เกมรุ่นใหม่" ยังใช้ `data.version` ซึ่งเป็น content hash ของไฟล์จริง (`computeServerVersion`)
  แยกหน้าที่จาก Running Version ชัดเจน: เปลี่ยนเลข EB deployment อย่างเดียวไม่ได้บังคับ reload และ restart process
  อย่างเดียวก็ไม่ทำให้เกิด version hash ใหม่ถ้าไฟล์ไม่เปลี่ยน
- จุดแจ้งอัปเดตอยู่ที่ `public/js/index.auto-update.js` เท่านั้น; `host.html`/`player.html` ไม่ popup หรือ reload
  เพียงเพราะ deployment ใหม่เกิดขึ้น

## อัปเดต: แก้บั๊ก คีย์บอร์ดมือถือดันทั้งหน้าขึ้นไปหมด (ฝั่งผู้เล่น `public/player.html`)

เดิม `.app` (คอนเทนเนอร์หลักฝั่งผู้เล่น) ล็อกความสูงด้วย `100dvh` (dynamic viewport height) ซึ่งในบาง
เบราว์เซอร์ (โดยเฉพาะ Android Chrome) ค่านี้จะยุบตามพื้นที่ที่คีย์บอร์ดมือถือมากิน ทำให้พอแตะช่องพิมพ์แชท
ทั้งเลย์เอาต์ (กริดผู้เล่น/แชท/บาร์ล่าง) ถูกบีบ/ดันกระโดดขึ้นไปพร้อมกันหมด มองไม่ค่อยเห็นว่ากำลังพิมพ์
อะไรอยู่ — แก้ 2 ชั้นพร้อมกัน:

1. **ล็อกเลย์เอาต์หลักไม่ให้ขยับตามคีย์บอร์ดอีกต่อไป** — เปลี่ยน `<meta name="viewport">`
   (`public/player.html`) เพิ่ม `interactive-widget=resizes-visual` (บอกเบราว์เซอร์ให้ย่อแค่
   "visual viewport" ตอนคีย์บอร์ดเปิด ห้ามย่อ layout viewport ตาม) คู่กับเปลี่ยนหน่วยความสูงของ
   `html`/`body`/`.app` (`public/css/player.css`) จาก `100dvh` เป็น `100svh` (small viewport height —
   ไม่ขยับตามคีย์บอร์ด) เป็นเซฟตี้อีกชั้นสำหรับเบราว์เซอร์ที่ยังไม่รองรับ `interactive-widget`
2. **ช่องพิมพ์แชทลอยขึ้นไปเกาะขอบบนคีย์บอร์ดเองแยกต่างหาก** — เพราะพอเลย์เอาต์หลักถูกล็อกนิ่งแล้ว
   (ข้อ 1) ช่องพิมพ์ที่อยู่ล่างสุดของ `.app` จะไปโผล่อยู่ใต้คีย์บอร์ดพอดี (มองไม่เห็น) เพิ่ม
   `id="chatRow"` ให้ `.chatRow` (คอนเทนเนอร์ของ `#silencedNotice` + `#chatInputRow`) แล้วใช้
   `VisualViewport` API (ท้าย `public/js/player.main.js`) คำนวณความสูงคีย์บอร์ดจริง (ไม่เดาค่าคงที่)
   ตั้ง `transform:translateY(-Npx)` แบบ inline ให้ลอยขึ้นพอดีกับขอบบนคีย์บอร์ด พร้อมสลับคลาส
   `.chatRow.kb-floating` (`public/css/player.css`) ให้มีพื้นหลัง/เงาตอนลอย (เพราะพื้นที่ `.app` ไม่ขยับ
   ตาม ช่องพิมพ์เลยไปลอยทับข้อความแชทแถวล่างสุดชั่วคราว) — `.chatRow` มี `transition:transform` ประจำ
   อยู่แล้วเสมอ (ไม่ใช่แค่ตอน floating) ทำให้ทั้งตอนลอยขึ้นและย้ายกลับที่เดิมตอนปิดคีย์บอร์ดสมูททั้งสองทาง
   โดยอัตโนมัติ ไม่ต้องเขียนอนิเมชั่นแยกเอง

**ขอบเขต:** แก้เฉพาะฝั่งผู้เล่น (`public/player.html`) ซึ่งเป็นจุดที่ล็อกความสูงด้วย `dvh` แต่แรก
(`public/host.html` ไม่มีปัญหานี้ เพราะเป็นหน้าที่เลื่อนได้ปกติ ไม่ได้ล็อกความสูงคอนเทนเนอร์แบบเดียวกัน)

## อัปเดต: แก้บั๊ก กริดผู้เล่น (โฮสต์) พังถ้าพิมพ์จำนวนคอลัมน์เกิน 20

`min="1" max="20"` ไว้ แต่ attribute `max` ของ `<input type="number">` **บล็อกแค่ปุ่มลูกศร
increment/decrement เท่านั้น ไม่ได้บล็อกค่าที่พิมพ์เข้ามาตรงๆ** ทางฝั่ง `onGridColsInputChange()`
(`public/js/host.main.js`) เดิมเช็คแค่ `n >= 1` ไม่มีเพดานบน พิมพ์เลขเกิน 20 ได้อิสระ (เช่น 50, 999)
แล้วค่านั้นถูกส่งตรงเข้า `applyGridCols()` กลายเป็น `grid-template-columns:repeat(n, 1fr)` บังคับ
จำนวนคอลัมน์เท่านั้นบนความกว้างจอเท่าเดิม ทำให้การ์ดผู้เล่นทุกใบถูกบีบแคบจนแทบมองไม่เห็น/กดอะไรไม่ได้
เลย (โดยเฉพาะมือถือที่จอแคบอยู่แล้ว) — แก้โดย clamp ค่าที่ `onGridColsInputChange()` ให้อยู่ในช่วง 1-20
เดียวกับที่ประกาศไว้ใน HTML เสมอ ก่อนเก็บลง `gridColsByBreakpoint`/ส่งเข้า `applyGridCols()` พร้อมดึงเลข
ในช่องกลับมาให้ตรงค่าที่ใช้จริงด้วย (เผื่อผู้ใช้พิมพ์เกิน จะเห็นเลขในช่องถูกปรับกลับมาเป็น 20 ให้เอง)

## อัปเดต: แก้บั๊ก ปุ่ม/ช่องปรับจำนวนคอลัมน์กริดผู้เล่น (โฮสต์) กดแล้วไม่มีอะไรเกิดขึ้นเลย (ราก) — TDZ crash

บั๊กจริงที่ทำให้ "การแสดงผู้เล่นในห้องโฮสต์" ใช้งานไม่ได้เลยตั้งแต่โหลดหน้า: บล็อกโค้ดตัวปรับคอลัมน์กริด
(`GRID_COLS_DEFAULTS`/`gridColsByBreakpoint`/`currentGridBreakpoint` + ฟังก์ชัน `getGridBreakpoint`/
`applyGridCols`/`syncGridColsUI`/`refreshGridColsForBreakpoint`/`setGridColsPreset`/
`onGridColsInputChange`) เดิมถูกวางไว้ "ท้ายไฟล์" `public/js/host.main.js` ต่อจากบรรทัด
`renderRoles(); updateNightFlowButtons({started:false,...});` (initial empty-state render ตอนโหลดหน้า
ครั้งแรก) — แต่ `updateNightFlowButtons()` เรียก `refreshGridColsForBreakpoint()` อยู่ข้างในด้วย ซึ่งอ่านค่า
`currentGridBreakpoint`/`gridColsByBreakpoint` ที่ตอนนั้นยังไม่ถูกประกาศเลย (อยู่ถัดลงไปอีกหลายสิบบรรทัด)
→ ชน **temporal dead zone** ของ `let`/`const` โยน `Cannot access 'currentGridBreakpoint' before
initialization` ทันทีทุกครั้งที่โหลดหน้า (ยืนยันด้วยการรัน headless browser จำลองจริงแล้วเจอ error นี้เป๊ะๆ)

ผลที่ตามมา: exception ทำให้สคริปต์ท้ายไฟล์ที่เหลือทั้งหมดไม่ทำงานเลยสักบรรทัด รวมถึงบรรทัด
`let currentGridBreakpoint = null;` เองก็เลยไม่เคยถูกรันจริง ตัวแปรนี้เลยค้างอยู่ใน temporal dead zone
**ตลอดไปตั้งแต่โหลดหน้าเสร็จ** — กดปุ่มลัด 2/4/5/8 หรือพิมพ์เลขในช่องเมื่อไหร่ก็ชน error เดิมซ้ำแบบเงียบๆ
(เห็นเฉพาะใน console) ไม่มีผลอะไรบนหน้าจอเลย ตรงกับอาการที่รายงานมา ("ปุ่มให้เลือกกดก็ยังไม่มีอะไรโผล่")
และ `window.addEventListener("resize"/"orientationchange", refreshGridColsForBreakpoint)` ก็ไม่เคยถูก
ผูกไว้เช่นกัน (พลิกจอ/ย่อจอก็ไม่อัปเดตคอลัมน์ตามไปด้วย)

**แก้โดยย้ายทั้งบล็อก** (ตัวแปร + ฟังก์ชันทั้งหมด + การเรียก `refreshGridColsForBreakpoint()` ครั้งแรก +
การผูก resize/orientationchange) ไปไว้ **ก่อน** `renderRoles(); updateNightFlowButtons(...)` แทน
เพื่อให้ตัวแปร/ฟังก์ชันถูกประกาศพร้อมใช้งานจริงก่อนถูกเรียกใช้ครั้งแรกเสมอ — ทดสอบซ้ำด้วย headless browser
แล้ว ไม่มี error อีก และกดปุ่มเปลี่ยนคอลัมน์ได้จริง (ยืนยันด้วยการอ่านค่า `getComputedStyle` ก่อน/หลังกด)

## อัปเดต: แก้บั๊ก ช่องติ๊กสถานะผู้เล่น (มีชีวิต/ปกป้อง/เล็งฆ่า/ใบ้) มองไม่เห็นคำเลยเมื่อการ์ดแคบ

ต่อเนื่องจากฟีเจอร์ตัวปรับจำนวนคอลัมน์กริดผู้เล่นด้านบน — ตั้งคอลัมน์เยอะๆ (เช่น 8-20 คอลัมน์) ทำให้
การ์ดผู้เล่นแต่ละใบแคบลงมาก จนพื้นที่เหลือให้ข้อความในช่องติ๊ก 4 อัน (`มีชีวิต`/`ปกป้อง`/`เล็งฆ่า`/`ใบ้`
ใน `.toggles` ของ `renderPlayers()` และ `.srow-status` ของ `renderSimplePlayerList()` ใน
`public/js/host.main.js`) แทบไม่เหลือเลย — เดิม `.toggle .toggle-label` (`public/css/host.css`) มีแค่
`overflow:hidden; text-overflow:ellipsis` แต่ไม่มีจุดตัดสินใจว่า "แคบแค่ไหนถึงต้องเปลี่ยนเลย์เอาต์" เลย
ทำให้ช่องติ๊ก 2 คอลัมน์ต่อแถวยังบังคับอยู่แม้พื้นที่จริงจะเหลือไม่ถึงความกว้างของตัวช่องติ๊ก+padding เอง
ด้วยซ้ำ (checkbox 20px + gap + padding ก็กินพื้นที่เกินที่มีอยู่แล้ว) ข้อความเลยโดนตัดจนเหลือ 0
ตัวอักษร — มองไม่เห็นคำเลยจริงๆ ตรงกับอาการที่รายงานมา

**แก้โดย 3 ทาง ทำงานร่วมกัน:**

1. **Container query** (`@container playercard`) — เพิ่ม `container-type:inline-size;
   container-name:playercard;` ให้ `.player` (กริดปกติ) และ `.simple-row` (ลิสต์อย่างง่าย) ทั้งคู่
   (`public/css/host.css`) ให้ CSS อ่าน "ความกว้างจริงของการ์ดใบนั้น" ได้ตรงๆ แทนที่จะเดาจากความกว้างจอ
   (`@media`) ซึ่งไม่แม่นเพราะการ์ดเดียวกันแคบ/กว้างไม่เท่ากันขึ้นอยู่กับจำนวนคอลัมน์ที่โฮสต์ตั้งไว้ตอนนั้น
   ไม่ใช่ขนาดจอ
2. **การ์ดแคบปานกลาง (≤190px)** — ยุบ `.toggles`/`.srow-status` จาก 2 คอลัมน์เหลือ 1 คอลัมน์ (แถวเดียว)
   ให้แต่ละปุ่มได้ความกว้างเต็มการ์ด ข้อความส่วนใหญ่จะพอมีที่ยืดอ่านออกโดยไม่ต้องตัดเลย
3. **การ์ดแคบมากจริงๆ (≤100px)** — ซ่อนข้อความ (`.toggle-label`) เปลี่ยนไปโชว์ไอคอนแทน (`.toggle-icon`
   — เพิ่ม `<span class="toggle-icon">` คู่กับ `.toggle-label` เดิมทุกช่องใน `host.main.js`: ❤️ มีชีวิต,
   🛡️ ปกป้อง, 🎯 เล็งฆ่า, 🤐 ใบ้) ยังกดติ๊กได้ปกติทุกอย่าง แค่เปลี่ยนตัวที่โชว์ ดูความหมายเต็มได้จาก
   `title` tooltip ของแต่ละ `<label>` (เพิ่ม `title` ให้ครบทุกช่องแล้ว เดิมมีแค่ตอน "กำลังถูกเล็ง/ปกป้อง/
   ใบ้อยู่" เท่านั้น ตอนสถานะปกติไม่มี title เลย)

ไม่กระทบเลย์เอาต์ปกติ (จำนวนคอลัมน์น้อย/การ์ดกว้างพอ) เพราะ container query เป็น progressive
enhancement เข้ามาแทนที่เฉพาะตอนพื้นที่จริงไม่พอเท่านั้น

  - **รีเฟรช/เปิดเว็บใหม่ระหว่างปิดแล้วเข้าไม่ได้** กันที่ฝั่ง server จริง (ไม่ใช่แค่ซ่อนหน้าจอ): middleware ก่อน `express.static` ตอบ `public/maintenance.html` แทนทุกหน้าเกม (`/`, `*.html`, path ไม่มีนามสกุล), บล็อก asset/API เกมด้วย 503, `io.use` ปฏิเสธ socket (`connect_error` message = `server_closed`), และ `socket.on` wrapper ทิ้ง event เกมทุกตัวซ้ำอีกชั้น (ไม่ตอบ callback ตั้งใจ ไม่งั้น `join_room` ตอบ error แล้วหน้าเกมจะลบ `ww_joinedRoom` ที่จำห้องเดิมไว้)
  - ผ่านด่านได้เฉพาะ: `admin.html`, `maintenance.html`, ไอคอน, `/api/config`, `/api/admin/*`, และ socket ที่ต่อด้วย `auth: { admin: true }` (หน้า admin ไม่มี login อยู่แล้วก่อนหน้านี้ ไม่ได้เพิ่มช่องโหว่ใหม่)
  - หน้า "กำลังปิด" ตอบ **HTTP 200 ไม่ใช่ 503 ตั้งใจ** — Elastic Beanstalk/Load Balancer เช็คสุขภาพที่ `/` ถ้าได้ 503 อาจถอย deploy หรือสั่งเปลี่ยนเครื่อง; ส่ง `Cache-Control: no-store` กันหน้านี้ถูกแคชค้างหลังเปิดเซิร์ฟเวอร์
  - เปิดคืน: หน้า "กำลังปิด" (และ overlay ในหน้าเกม) เช็ค `/api/config` ทุก ~4 วิ พอ `serverOpen=true` จึงล้างห้องที่จำไว้แล้วพากลับ **หน้าแรก** (กระจายเวลาสุ่ม ≤2.5 วิ) — รีโหลดเฉพาะเมื่อได้คำตอบชัดว่าเปิดแล้ว เน็ตหลุดไม่ทำให้รีโหลด
  - **สถานะ "ปิด" + `imageEpoch` เก็บใน DynamoDB** แถว `__SYSTEM__` / `SERVER_STATE` (ตารางเดิม สิทธิ์ Get/Put เดิมที่ resetEpoch ใช้ — ไม่ต้องเพิ่ม IAM; `/api/admin/reset` ไม่ลบแถวนี้; หน้ารายชื่อผู้เล่นกรองแค่ `REG` จึงไม่ปนกัน) ทำให้ deploy/รีสตาร์ทตอนปิดอยู่แล้วยังคงปิด
  - ตอนบูตทุก request/socket รอโหลดสถานะไม่เกิน ~3 วิ (กันคนหลุดเข้าก่อนรู้ว่ายังปิดอยู่) ถ้า DynamoDB โหลดไม่ได้ = เปิดตามปกติ (fail-open) แล้วลองใหม่ทุก 10 วิ (สูงสุด 6 ครั้ง) ถ้าโหลดได้ทีหลังพบว่าปิดอยู่ก็ปิดตาม (ยกเว้นแอดมินสั่งเปิด/ปิดเองไปแล้ว)

**ไฟล์ที่เพิ่ม/แก้:** `server.js`, `public/admin.html`, `public/maintenance.html` (ใหม่), `public/js/shared.server-control.js` (ใหม่ — โหลดใน index/player/host หลัง `shared.reset-guard.js`), `public/js/player.main.js` + `host.main.js` (ต่อ event `force_reload`/`server_closed`/`connect_error` + `wwImg`), `public/index.html`/`player.html`/`host.html` (แท็ก script)

**ข้อจำกัดที่รู้อยู่แล้ว:** เลขรุ่นการสั่งรีโหลด (`reloadEpoch`) ไม่เก็บลง DB ตั้งใจ (รีสตาร์ทจริง = deploy ที่ระบบ auto-update เดิมดูแลอยู่แล้ว); ตัวจับเวลาในเกมระหว่างปิดเซิร์ฟเวอร์ไม่ได้ถูกหยุด

## อัปเดต: ปิด/เปิดเซิร์ฟเวอร์ + บังคับรีโหลด = จบเซสชัน (ปิดทุกห้อง ไม่นับสถิติ แล้วพากลับหน้าแรก)

**ปัญหาเดิม:** ปิดเซิร์ฟเวอร์แล้วห้องยังค้างในหน่วยความจำ ผู้เล่นที่ถูกตัด socket สะสมเวลาออฟไลน์ (`markPlayerOfflineStart`)
พอจบเกมเลยโดนนับ "ออกเกม" (ดู `didLeaveGame`) ทั้งที่ไม่ได้หนีเอง และตอนเปิดคืนหน้าเกมพยายามกลับห้องเดิม/สร้างห้องใหม่เอง

**พฤติกรรมใหม่:**
- **ปิดเซิร์ฟเวอร์** → `closeAllRoomsSilently()` ปิดทุกห้อง "ทันที ก่อนตัด socket" — ไม่เรียก `endGame`/`recordGameStats` จึงไม่มีแพ้/ชนะ/ออกเกมเข้าประวัติใคร ไม่ยิง `room_closed` (กันข้อความ "ผู้สร้างห้องออกจากเกม" ที่ไม่จริง) ไม่แตะ DynamoDB (ชื่อ/สถิติเดิมอยู่ครบ)
- **บังคับรีโหลดทั้ง 3 แบบ** (ไฟล์เกม/รูปภาพ/ทั้งสอง) → ปิดทุกห้องแบบเดียวกัน ก่อนยิง `force_reload`
- ทั้งสองอย่างเปลี่ยน `reloadEpoch` (`reloadKind` = `"session"` สำหรับปิด/เปิดเซิร์ฟเวอร์) — เปลี่ยนทั้งตอน "ปิด" และตอน "เปิด" (ระหว่างปิดอาจมี deploy/รีสตาร์ทคั่น ทำให้เลขในหน่วยความจำหาย) เฉพาะเมื่อสถานะเปลี่ยนจริง กดซ้ำสถานะเดิม (`changed:false`) ไม่ทำอะไร ไม่ไล่คนที่กำลังเล่น
- **ฝั่ง client** (`shared.server-control.js`): ทุกเส้นทาง (ได้ `force_reload` / เห็นเลข epoch ไม่ตรง / เปิดคืนหลังเห็นจอ "กำลังปิด") จบที่ `goHome()` = ล้างคีย์ผูกห้อง (`ww_joinedRoom`, `ww_lastRoom`, `ww_token`, `ww_host_room`, `ww_host_token`, `ww_bot_tokens`, `ww_room_pass_*`, `ww_room_joincode_*`) ทั้ง localStorage/sessionStorage แล้ว `location.replace("/")` (อยู่หน้าแรกอยู่แล้วก็รีโหลด) — **ไม่ล้าง** ชื่อผู้เล่น (`ww_playerName`, `ww_host_display_name`) และสถานะผ่านรหัสโฮสต์/ผู้ทดสอบ
- "ไฟล์เกม"/"ทั้งสอง": ล้างแคชของหน้าปัจจุบัน **และหน้าแรกปลายทาง** (`cache:"reload"`) ก่อนไป
- `public/maintenance.html` (และหน้าสำรองใน `server.js`): พอเปิดคืนจะล้างคีย์เดียวกันแล้วไป `/` เสมอ (ไม่รีโหลดหน้าเกมเดิม)
- หน้า admin: แก้ข้อความยืนยัน/ผลลัพธ์ ให้เตือนว่าจะปิดทุกห้อง และโชว์จำนวนห้องที่ปิด
- response ของ `/api/admin/server-open` และ `/api/admin/force-reload` เพิ่ม `closedRooms` (และ `changed` สำหรับ server-open)

**ไฟล์ที่แก้:** `server.js`, `public/js/shared.server-control.js`, `public/maintenance.html`, `public/admin.html`

**ข้อจำกัดที่รู้อยู่แล้ว:** รีสตาร์ท process จริงโดยไม่กดปุ่มปิด/เปิด พฤติกรรมเดิม (ห้องหายเอง ผู้เล่นเห็นหน้ากรอกห้อง ไม่ได้ถูกพากลับ index); ปุ่ม "รูปภาพ" อย่างเดียวก็ปิดทุกห้องด้วย (ตั้งใจ ตามคำขอให้รวมการบังคับรีทุกแบบ) ถ้าอยากให้ไม่ยุ่งกับเกม ให้ข้าม `closeAllRoomsSilently()` เมื่อ `kind === "images"` ใน `/api/admin/force-reload`

## อัปเดต: ปิดเซิร์ฟเวอร์แบบนับถอยหลัง + ประกาศข้อความ + เวลาที่คาดว่าจะเปิด (แท็บ ⚙️ จัดการระบบ)

**ปุ่ม "ปิดเซิร์ฟเวอร์" ตอนนี้มีกล่องกรอก 3 ช่อง** (ทั้งหมดไม่บังคับ):
- **ปิดในอีก**: ปิดทันที / 30 วิ / 1 / 2 / 5 / 10 นาที (ค่าเริ่มต้น 1 นาที; server จำกัดสูงสุด 900 วิ)
- **ข้อความถึงผู้เล่น**: ไม่เกิน 200 ตัวอักษร (server ตัดตัวควบคุม/ตัดความยาวให้)
- **คาดว่าจะเปิดในอีกกี่นาที** (นับหลังปิดจริง; สูงสุด 1440) — โชว์เป็นนาฬิกา "คาดว่าจะเปิดประมาณ HH:MM น. (อีกประมาณ N นาที)" ตามเวลาเครื่องผู้เล่นแต่ละคน

**ระหว่างนับถอยหลัง** (`closingPlan` ใน `server.js`): เซิร์ฟเวอร์ยังเปิด เล่นได้ปกติ แต่ทุกเครื่องเห็นแถบเตือนสีส้มด้านบน "⚠️ เซิร์ฟเวอร์จะปิดใน m:ss" + ข้อความ + เวลาที่คาดว่าจะเปิด (ไม่บังการกด: `pointer-events:none`)
- เครื่องที่เล่นอยู่ได้จาก socket `server_closing` / `server_closing_cancelled`; เครื่องที่ไม่มี socket (หน้าแรก/เครื่องที่เพิ่งตื่น) เห็นจาก `/api/config` (`closingInMs`, `noticeMessage`, `reopenAt`, `serverNow`) โพลทุก 5 วิระหว่างมีแถบ
- ส่ง "เวลาที่เหลือ" ไม่ใช่เวลาเป๊ะ (ไม่พึ่งนาฬิกาเครื่องผู้เล่น) และส่ง `serverNow` ให้คำนวณ "อีกกี่นาทีจะเปิด" ตรงแม้นาฬิกาเครื่องเพี้ยน
- **ครบเวลา** → `performServerClose()` = ปิดจริงเหมือนเดิม (ปิดทุกห้องแบบเงียบ ไม่นับสถิติ/ออกเกม → เปลี่ยน epoch → บันทึก DB)
- **ยกเลิกได้ก่อนครบ**: ปุ่ม "↩️ ยกเลิกการปิด" → `POST /api/admin/server-close-cancel` (ทุกเครื่องเห็น "แอดมินยกเลิกการปิดเซิร์ฟเวอร์ เล่นต่อได้")
- ตั้งเวลาซ้ำระหว่างนับ = แทนที่แผนเดิม · กด "เปิด" ระหว่างนับ = ยกเลิกแผน · กดสถานะเดิมซ้ำไม่ไล่ใคร

**หลังปิดจริง**: จอ "เซิร์ฟเวอร์กำลังปิด" (ทั้ง overlay ในหน้าเกมและ `maintenance.html`) โชว์ข้อความ + เวลาที่คาดว่าจะเปิด อัปเดตเองทุก ~4 วิ
- **แก้ข้อความ/เวลาระหว่างปิดได้**: ปุ่ม "✏️ แก้ข้อความ / เวลาที่คาดว่าจะเปิด" (`POST /api/admin/server-open { open:false, message, reopenInMin }` ตอนปิดอยู่ = อัปเดตอย่างเดียว ไม่แตะห้อง/epoch; เวลานับจากตอนนี้; ส่งว่าง = ลบ)
- ข้อความ + เวลาถูกเก็บลง DynamoDB (`SERVER_STATE`: `closedMessage`, `closedReopenAt`) พร้อมสถานะปิด → ยังโชว์ต่อหลัง deploy/รีสตาร์ทตอนปิดค้าง; เปิดคืนแล้วล้างทิ้ง
- ข้อความของแอดมินโชว์ด้วย `textContent` เสมอ (ไม่ใช้ `innerHTML`) กัน HTML/สคริปต์แทรก

**แก้บั๊กจากรอบก่อน (`public/maintenance.html`)**: ตอนแก้ไฟล์รอบ "ปิด/เปิด = จบเซสชัน" คำสั่ง `clearSessionIdentity()` บนหน้า "กำลังปิด" ถูกต่อท้ายบรรทัดคอมเมนต์โดยไม่ตั้งใจ (ไม่ทำงาน) → เครื่องที่รอที่หน้านั้นไปหน้าแรกได้ แต่ ห้อง/token ที่จำไว้ไม่ถูกล้าง ตอนนี้แก้แล้วและมีเทสต์ครอบ

**ไฟล์ที่แก้:** `server.js`, `public/admin.html`, `public/maintenance.html`, `public/js/shared.server-control.js`, `public/js/player.main.js` + `host.main.js` (ต่อ event `server_closing` / `server_closing_cancelled`)

**ข้อจำกัดที่รู้อยู่แล้ว:** การนับถอยหลังที่ค้างไว้ไม่ถูกเก็บลง DB — รีสตาร์ท process ระหว่างนับ = ถือว่ายกเลิก (ห้องในหน่วยความจำหายเองอยู่แล้ว)


## อัปเดต: ย้ายปุ่ม "เข้าในฐานะผู้ทดสอบ" จากหน้าแรกไปอยู่ใน `public/admin.html`

- **หน้าแรก (`index.html`)**: ลบปุ่ม "🧪 เข้าในฐานะผู้ทดสอบ" + ป๊อปอัปเลือกโฮสต์/ผู้เล่น (`#testerModal`) ออกทั้งหมด
  พร้อมโค้ดใน `index.main.js` (`openTesterModal`/`pickTesterRole`/`confirmTester`/`closeTesterModal`) และ CSS
  ที่ใช้เฉพาะปุ่มนี้ (`.btn-tester`, `.tester-role-*`) — ผู้เล่นทั่วไปไม่เห็นทางเข้านี้อีก
- **หน้าแอดมิน (`admin.html`)**: แท็บ ⚙️ จัดการระบบ มีการ์ด "🧪 เข้าในฐานะผู้ทดสอบ" — เลือก โฮสต์/ผู้เล่น + ช่องชื่อ
  (เติมให้จากชื่อที่ตั้งไว้ในเครื่อง แก้ได้ แต่ไม่เขียนกลับ) แล้วกด "เข้าใช้งาน" → เปิด
  `host.html?tester=1&name=...` หรือ `player.html?tester=1&name=...` **ในแท็บใหม่** (`noopener` กัน sessionStorage
  ของหน้าแอดมินถูก clone ติดไป) กดซ้ำได้เรื่อยๆ = ได้บัญชีทดสอบเพิ่มทีละแท็บ
- **ที่ไม่เปลี่ยน**: ตัวโหมดผู้ทดสอบฝั่งเกม (`?tester=1` ใน `host.main.js`/`player.main.js`/`server.js`) ทำงานเหมือนเดิมทุกอย่าง
  — ย้ายแค่ "ทางเข้า" ต้องเข้าผ่าน URL ตรงๆ ก็ยังได้อยู่ (หน้า admin ไม่มี login ดูคอมเมนต์ใน `server.js`) จึงเป็นการซ่อนปุ่ม
  ไม่ใช่การล็อกสิทธิ์

### เพิ่ม: โหมดผู้ทดสอบจากหน้า admin เข้าเล่นได้แม้ปิดเซิร์ฟเวอร์อยู่ ("บัตรผ่านผู้ทดสอบ")

ไว้ลองเล่นอัปเดตใหม่หลัง deploy ตอนที่ยังปิดเซิร์ฟเวอร์ค้างไว้ — ผู้เล่นทั่วไปยังเข้าไม่ได้เหมือนเดิม

- **วิธีทำงาน**: หน้า admin ขอบัตรผ่านที่ `POST /api/admin/tester-pass` (ต้องใส่รหัสผ่านแอดมินถ้าตั้ง `ADMIN_RESET_PASSWORD` —
  ช่องรหัสจะโผล่ในการ์ดเอง) ได้ token สุ่มอายุ 12 ชม. เก็บในหน่วยความจำ แล้วเปิดแท็บทดสอบพร้อม `&tp=<token>`
  → server ฝัง cookie `ww_tp` (HttpOnly) ตอนโหลดหน้า → หน้า/js/css/รูป/`/api/*`/socket ของแท็บนั้นผ่านด่านตอนปิดได้ทั้งหมด
  (ฝั่ง client ไม่ต้องแก้ — `/api/config` บอกผู้ถือบัตรว่า `serverOpen = true` จึงไม่ขึ้นจอ "กำลังปิด")
- **ตอนกดปิดเซิร์ฟเวอร์**: แท็บทดสอบที่เปิดอยู่ไม่ถูกตัด/ไม่เห็นจอ "กำลังปิด" และห้องผู้ทดสอบไม่ถูกปิด (โฮสต์/ผู้เล่น/บอท/การเข้าสิงเล่นต่อได้)
- **ตอนกดปิด/เปิดเซิร์ฟเวอร์/รีโหลด**: ~~ห้องทดสอบถูกปิด~~ (ล้าสมัย) — ตอนนี้ห้องผู้ทดสอบ **ไม่ถูกปิด/ไม่ถูกพากลับหน้าแรก** ดูหัวข้อ "แจ้งอัปเดตเฉพาะหน้า index + โหมดผู้ทดสอบอยู่นอกวงจรปิดเซิร์ฟเวอร์" ท้ายไฟล์
- **หน้า admin เห็นสถานะจริง**: เครื่องแอดมินถือ cookie บัตรผ่านเลยเห็น `serverOpen` เป็นเปิดตลอด จึงเปลี่ยนให้ admin เรียก `/api/config?real=1` (ข้ามบัตรผ่าน)
- **แก้แล้ว**: บัตรผู้ทดสอบใช้ signed token + secret ที่คงเดิมข้าม process/instance/restart (เก็บ secret ใน SERVER_STATE ของ DynamoDB หรือใช้ `TESTER_PASS_SECRET` จาก environment); token หมดอายุตาม TTL 12 ชม. เอง
  cookie ยังคงผูกกับเบราว์เซอร์ทั้งตัวตามสถาปัตยกรรมเดิม — เครื่องแอดมินที่ถือบัตรจึงผ่านด่านปิดเซิร์ฟเวอร์ได้ในทุกแท็บ (ตั้งใจ)

  **มือถือมีข้อจำกัดของ Web Platform**: ตอน OS/browser kill process จาก app manager หรือกรณี lifecycle event ไม่ถูกส่ง เว็บรับประกัน dialog/exit callback 100% ไม่ได้

### อัปเดต: Browser Tab Close Guard v19 (Host + Player)
- **Host**: เมื่อกำลังคุมห้อง `beforeunload` จะถามด้วย dialog ของ browser; เมื่อผู้ใช้ยืนยันออก `pagehide` ส่ง `/api/room/browser-exit-host` แบบ `sendBeacon`/`fetch keepalive`
  server รอ ~4 วินาทีเพื่อให้ Host เดิม reconnect ได้ก่อนปิดจริง และถ้ามี `hostIds` อื่นที่ยัง connected อยู่จะ **ไม่ปิดห้อง**; ปิดจริงเมื่อไม่เหลือ host screen
- **Player**: เมื่ออยู่ในห้อง `beforeunload` จะถามด้วย dialog ของ browser; server รอ ~3 วินาทีเพื่อกัน reload/reconnect แล้วค่อยเอาออกจาก lobby หรือ (ถ้าเกมเริ่มแล้ว) ใช้เส้นทาง voluntary leave ที่บันทึกสถิติ + ทำให้ตายทันที + cleanup เอฟเฟกต์ + ประกาศ `🚪 <ชื่อ> ออกจากเกม` ตามกติกาเดิม
- **ไม่ใช้ `disconnect` เป็นหลักในการตัดสินว่า "ปิดแท็บจริง"** เพราะ disconnect สามารถเกิดจาก network/app switch/reconnect ได้
- **Diagnostic causal graph**: `browser_exit_signal → browser_exit_armed → browser_exit_cancelled` หรือ `browser_exit_signal → browser_exit_armed → browser_exit_applied → room_closed_after_browser_exit / PLAYER_LEFT_GAME` ถูกบันทึกเป็น Event ID และ explicit upstream/downstream links ทำให้รายงาน Share มีลิงก์ย้อนหาต้นเหตุและเดินหน้าดูผลกระทบต่อทีละ log
- `wwConfirm(message, { okText, cancelText, danger })` (`ww-ui.js`) รับตัวเลือกเสริมสำหรับข้อความปุ่ม/ปุ่มสีแดง — ไม่ส่งมา = เหมือนเดิมทุกอย่าง

## อัปเดต: แจ้งอัปเดตเฉพาะหน้า index + โหมดผู้ทดสอบอยู่นอกวงจรปิดเซิร์ฟเวอร์

### หลักการ (ห้ามทำให้กลับไปเป็นแบบเดิม)
```
มีไฟล์รุ่นใหม่ (deploy)
   ├─ คนที่กำลังเล่น (host/player) → ไม่ทำอะไรเลย: ไม่ popup / ไม่ reload / ไม่ redirect
   └─ พอกลับหน้า index เอง → เทียบ version → overlay "มีอัปเดตเกมใหม่" → ผู้ใช้กดปุ่ม → ล้างแคช → โหลดรุ่นใหม่
```
- `host.html` / `player.html` **ไม่มีสคริปต์ตรวจอัปเดตเลย** (ลบ `host.auto-update.js`, `player.auto-update.js`, ลบ `wwCheckVersion` ทุกจุด) — จุดเดียวคือ `public/js/index.auto-update.js`
- `shared.server-control.js` ยังโพล `/api/config` เพื่อ "คำสั่งแอดมิน" (ปิดเซิร์ฟเวอร์/บังคับรีโหลด) แต่ **ไม่อ่าน `version`** และเติมแค่ `WW_IMG_BASE` + ป้ายเวอร์ชัน
- บั๊กเดิม: overlay ใน `index.html` ตั้ง `display:none` แบบ inline ทำให้ rule `.show` ไม่เคยทำงาน (overlay ไม่เคยโผล่) — ย้าย `display` ไปไว้ใน `<style>`

### Version = เนื้อหาไฟล์จริง (`server.js`: `computeServerVersion`)
- hash จาก: `public/**/*.{html,js,css,json,svg,...}` (ยกเว้น `admin.html`, `maintenance.html`) + asset/รูป (`public/**` รวม `public/images/**`) + `server.js`, `botEngine.js`, `llmBotEngine.js` + `imageEpoch` (สำหรับรูปบน S3/CDN ที่ server อ่านเนื้อหาไม่ได้)
- **ไม่มี `BOOT_TIME` แล้ว** → Node restart ที่ไฟล์เหมือนเดิม/หลาย instance ให้ค่าเดียวกัน; แค่ mtime เปลี่ยนไม่ทำให้ version เปลี่ยน
- หน้า index/host/player ถูกเสิร์ฟพร้อม `?v=<hash>` ต่อท้าย js/css (`STAMPED_PAGES`) — HTML ชุดไหนก็ได้ js/css ชุดเดียวกับตัวเอง (กัน Android/iOS ได้ไฟล์ปนรุ่น)
- URL รูปทุกใบต่อ `?v=` = เลขที่แอดมินกด + hash รูปใน `public/` (เปลี่ยนรูปแล้ว URL เปลี่ยนเอง)
- `/api/config` ส่ง `Cache-Control: no-store`
- **แยก "ประกาศรุ่นใหม่" ออกจาก "ปิดห้อง"**: `POST /api/admin/publish-update` (ปุ่ม 📣 ใน admin) เปลี่ยน version โดยไม่ปิดห้อง/ไม่ยิง `force_reload`; ส่วน `force-reload` และ `server-open` คือ "ปิดห้องปกติ" ที่ต้องกดเอง — การ deploy ไม่เรียกทั้งสองอย่าง

### โหมดผู้ทดสอบ (server ตัดสินสิทธิ์เอง)
- ห้องเป็น "ห้องผู้ทดสอบ" (`room.isTesterRoom`) ก็ต่อเมื่อ socket ที่สร้างห้องถือ **Tester Pass ที่ server ออกให้** (cookie `ww_tp`) และ client ขอโหมดผู้ทดสอบ — `isTester` ที่ client ส่งมาอย่างเดียว (หรือ `handshake.auth.isTester`) ไม่มีผล (`resolveTesterFlag`)
- `closeAllRoomsSilently()` ข้ามห้องผู้ทดสอบ (ห้อง/บอท/โทเค็นสิง/timer อยู่ครบ); `force_reload` / `server_closed` / `server_closing` ไม่ส่งให้ socket ที่ได้รับการคุ้มครอง (`isProtectedSocket`); `/api/config` ไม่ส่ง `reloadEpoch`/นับถอยหลังให้เครื่องที่ถือบัตรหรือส่ง token สมาชิกห้องผู้ทดสอบมา (header `X-WW-Room`/`X-WW-Token`)
- `auth.admin` (ค่าที่ client ส่งเอง) ตอนปิดเซิร์ฟเวอร์ส่งได้เฉพาะ event `admin_*` แล้ว (เดิมเล่นเกมต่อได้)
- `/api/admin/reset` (ล้างข้อมูลทั้งระบบ) ยังล้าง **ทุกห้อง** รวมห้องผู้ทดสอบ (ตั้งใจ)

### หน้า "เซิร์ฟเวอร์กำลังปิด" (iPad/iPhone/Android)
- `GET /api/roles-data` (ข้อมูลชุดเดียวกับ socket `roles_data`, no-store, ไม่ต้อง login) และ `GET /images/*` ผ่านด่านตอนปิดได้; `maintenance.html` และ overlay ในหน้าเกมดึงข้อมูลอาชีพเองเมื่อไม่มีข้อมูลในเครื่อง
- แก้ `touch-action:none` ของ overlay ที่บล็อกการเลื่อนบนจอสัมผัส

### ข้อความตอน reconnect
- server ตอบ `code` เพิ่ม (`ROOM_NOT_FOUND`, `AUTH_FAILED`, `TOO_MANY_ATTEMPTS`, `ROOM_STARTED`, `ROOM_FULL`, `SERVER_ERROR`) โดยยังคง `error` เดิมไว้; `host.main.js`/`player.main.js` แยกข้อความตามสาเหตุ และ `SERVER_ERROR` ลองใหม่เงียบๆ ไม่พากลับเมนู

### ข้อจำกัดที่รู้อยู่แล้ว
- ห้องเกมที่ persistence บันทึกไว้จะกู้กลับได้หลัง Node restart/deploy แต่ถ้า DynamoDB ใช้งานไม่ได้ในช่วง recovery หรือ snapshot ล่าสุดเก่าเกิน TTL ห้องที่กู้ไม่ได้จะไม่ถูกสร้างกลับใน RAM
- การบันทึก snapshot เป็นแบบ debounce/periodic ดังนั้นหาก process ล่มทันทีระหว่างช่วงที่ยังไม่ได้เขียน snapshot การเปลี่ยนแปลงล่าสุดบางส่วนอาจหายได้; สถานะจะกู้จาก snapshot ล่าสุดที่บันทึกสำเร็จ
- สมาชิกห้องผู้ทดสอบที่ไม่มี Tester Pass ยังพึ่ง room token ที่ server ตรวจตอน reconnect — จึงกลับเข้าห้องผู้ทดสอบได้เมื่อ room snapshot ถูกกู้สำเร็จ
- ระบบปัจจุบันเหมาะกับการกู้หลัง process restart บน instance เดียว; ยังไม่ได้ทำ distributed room ownership/lease สำหรับหลาย Node หลาย instance ที่รับห้องเดียวกันพร้อมกัน
- `pageshow` (`persisted`) ใน `shared.server-control.js` ยัง `location.reload()` เฉพาะตอนเบราว์เซอร์กู้หน้าจาก bfcache หลังผู้ใช้กดย้อนกลับเอง (ไม่เกี่ยวกับ version)
- ถ้า DynamoDB ตอบช้าเกิน ~3 วินาทีหลังบูต `imageEpoch` อาจเปลี่ยนหลังโหลดเสร็จ ทำให้ version เปลี่ยนหนึ่งครั้ง


## Durable room persistence / recovery

ระบบห้องเกมใช้ RAM เป็น runtime cache เพื่อให้การเล่นและ WebSocket ยังเร็วเหมือนเดิม แต่จะสร้าง room snapshot ลง DynamoDB เป็นระยะ และกู้คืน snapshot กลับเข้า RAM ก่อนรับ socket หลัง Node.js restart/deploy

ค่าเริ่มต้นจะใช้ตารางเดียวกับ `DYNAMODB_STATS_TABLE` เดิม เพื่อไม่ต้องสร้าง IAM/table เพิ่มทันที หากระบบโตขึ้นสามารถตั้ง `DYNAMODB_ROOMS_TABLE` เป็นตารางแยกได้ แต่ตารางนั้นต้องใช้ key schema เดียวกันคือ:

- Partition key: `playerName` (String)
- Sort key: `statKey` (String)

ระบบจะสร้างรายการหลักสองแบบ:

- `playerName="__SYSTEM__", statKey="ROOM_INDEX"` เก็บชุด roomId ที่ยัง active
- `playerName="__ROOM__:<ROOM_ID>", statKey="ROOM_SNAPSHOT"` เก็บ snapshot ของ state ห้อง

สิทธิ์ IAM ที่ instance role ต้องมีสำหรับตารางห้องคืออย่างน้อย `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, `BatchGetItem`, `BatchWriteItem` (ถ้าใช้ตารางสถิติเดิมอยู่แล้ว สิทธิ์ส่วนใหญ่มีอยู่จากระบบ reset/statistics ปัจจุบัน)

Environment ที่ตั้งได้:

- `ROOM_PERSISTENCE_ENABLED=true` (ค่าเริ่มต้น; สำหรับ local dev ปิดได้ด้วย `false`)
- `DYNAMODB_ROOMS_TABLE=<table-name>` (ไม่ตั้ง = ใช้ `DYNAMODB_STATS_TABLE`)
- `ROOM_PERSISTENCE_SCAN_MS=1500` ระยะตรวจ snapshot เปลี่ยนแปลง
- `ROOM_PERSISTENCE_DEBOUNCE_MS=750` เวลารวมการเปลี่ยนแปลงก่อนเขียน DB
- `ROOM_RECOVERY_TIMEOUT_MS=8000` เวลาสูงสุดที่ยอมรอ recovery ก่อน fail-open
- `ROOM_RECOVERY_TTL_MS=604800000` ค่าเริ่มต้น 7 วัน; snapshot ที่เก่ากว่านี้จะไม่ถูกกู้

### หลัง Node restart

1. Node โหลดสถานะ server จาก `SERVER_STATE`
2. โหลด `ROOM_INDEX`
3. Batch-get snapshot ของห้อง active
4. สร้าง `rooms[id]` กลับเข้า RAM
5. ล้าง `host/hostIds` ที่เป็น socket เก่า และ mark ผู้เล่นเป็น disconnected
6. ผู้เล่น/โฮสต์ reconnect ด้วย token เดิม แล้ว server remap ไปยัง `socket.id` ใหม่

Socket.io ฝั่ง client ของโปรเจกต์มี auto-reconnect/auto-rejoin อยู่แล้ว ดังนั้นการ restart process ไม่ควรเปลี่ยนเป็น `ROOM_NOT_FOUND` เพียงเพราะ socket หลุดชั่วคราว

### ขอบเขตการกู้คืน

- ห้องปกติที่ถูก admin ปิด/force-reload จะไม่ถูก resurrect จาก snapshot เก่า แม้ snapshot ลบทิ้งไม่สำเร็จ เพราะมี `roomResetAt` เป็น session cutoff
- ห้อง tester ยังถูกเก็บไว้ตามกฎเดิมของระบบทดสอบ
- `/api/admin/reset` จะล้าง room snapshots และ `ROOM_INDEX` ด้วย
- ไม่บันทึก Socket object หรือ timer handle ลง DB; สิ่งเหล่านั้นถูกสร้าง/ผูกใหม่ตอน runtime

ระบบนี้รองรับการ recovery หลัง process restart ได้ แต่ยังไม่ได้ทำ distributed room ownership เต็มรูปแบบสำหรับหลาย Node/หลาย instance พร้อมกัน หากจะ scale Elastic Beanstalk เป็นหลาย instance ในอนาคตควรเพิ่ม distributed lease/room ownership หรือใช้สถาปัตยกรรม realtime state ที่รองรับ multi-instance โดยตรง

- หน้า `admin.html` ยังเข้าได้ตรง ๆ ตามเดิมในรุ่นนี้ ยังไม่มีระบบรหัสผ่านสำหรับหน้า Admin ตามที่กำหนดไว้
- Game Account แยกจาก room reconnect token: `accountId` เป็นตัวตนของบัญชี, `accountToken` เป็น credential ฝั่งเครื่อง และ `ww_token`/`ww_host_token` ยังคงเป็น token สำหรับ reconnect ห้อง
- เปิดเกมครั้งแรกในโหมดปกติจะได้ Temporary Account อัตโนมัติ พร้อมชื่อสุ่มจาก server; ไม่ต้องรอ Admin ตั้งชื่อก่อนเล่น
- ผู้เล่นเปลี่ยนชื่อเองได้จาก Profile และชื่อไม่ใช่ตัวระบุบัญชี; การเปลี่ยนชื่อบันทึก alias และอัปเดตทุก session/ห้องที่ account เดียวกันกำลังใช้งานอยู่
- Temporary Account มี `temporaryExpiresAt` = server-confirmed activity ล่าสุด + 15 วัน; heartbeat/presence อย่างเดียวไม่ต่ออายุ จึงไม่สามารถต่ออายุด้วยการเปิดแท็บค้างไว้เฉย ๆ
- activity ที่ต่ออายุได้มาจากการสร้าง/ตรวจบัญชี, เข้าหรือ reconnect ห้อง, เปลี่ยนชื่อ, จบเกม และการเปิด Profile ผ่าน `account_touch`
- เมื่อ Temporary Account หมดอายุ ข้อมูล profile/stats/event ใต้ accountId นั้นจะถูกลบ และการกลับมาใช้งานจะได้ accountId ใหม่; ไม่มีการ restore account เดิม
- ถ้าบัญชีถูก Admin ลบ/ปิด session ฝั่ง client จะล้าง Game Account identity เดิมก่อนกลับหน้า index เพื่อไม่ให้ credential เก่ากลับเข้าบัญชีเดิมโดยอัตโนมัติ
- หน้า Admin แยกบัญชีจริงออกจาก Tester/Bot และสามารถดูบัญชีออฟไลน์ผ่าน `/api/admin/players` ได้ พร้อมชนิดบัญชีและวันหมดอายุของ Temporary Account
- Admin ใช้ `accountId` เป็นหลักสำหรับ rename/kick/suspend/delete/reset stats; `suspended` ตรวจบังคับที่ server ทุกครั้ง ไม่ใช่แค่สถานะบนหน้าเว็บ
- Tester และ Bot จะไม่ถูกสร้างเป็นบัญชีจริง และไม่ถูกบันทึกเข้า registry/stats/account history
- ข้อมูลบัญชีใหม่เก็บใน partition `playerName=__ACCOUNTS__` ของตาราง `DYNAMODB_STATS_TABLE` เดิม ไม่ต้องสร้าง DynamoDB table ใหม่
- Phase 2 ใช้ Google OAuth/OIDC โดยตรงเป็น external identity provider แยกจาก Game Account: Google `sub` ถูก map ไปยัง `accountId` และ Temporary Account ที่กด "เชื่อม Google" จะใช้ `accountId` เดิม
- Google session ของ Game Account ใช้ credential คนละชุดกับ room reconnect token และหมดอายุใน 30 วัน; การออกจากระบบเพิกถอนเฉพาะ session ของเครื่องนั้น
- OAuth authorization state, account-link context และ PKCE verifier เก็บใน HttpOnly signed cookie; ไม่ส่ง `accountToken` ดิบไปกับ Google URL
- `/api/player-stats` ฝั่ง account ใช้ `X-WW-Account-Token` header แทนการใส่ credential ใน URL
- Admin API/Socket ที่ขึ้นต้น `admin_*` ต้องผ่าน HttpOnly admin session เสมอ; ถ้าตั้ง `ADMIN_PANEL_PASSWORD` จะเข้าได้ด้วยรหัสแอดมิน และถ้าตั้ง `ADMIN_GOOGLE_EMAILS` จะเข้าได้ด้วย Google เฉพาะอีเมลที่ whitelist และ `email_verified=true`; `auth.admin=true` ใน Socket.IO เพียงอย่างเดียวไม่ถือเป็นสิทธิ์
- ถ้าไม่ได้ตั้งทั้ง `ADMIN_PANEL_PASSWORD` และ `ADMIN_GOOGLE_EMAILS` ระบบจะ **fail-closed**: API แอดมินตอบ `503 ADMIN_AUTH_NOT_CONFIGURED` และ socket ไม่ให้ใช้ `admin_*`

### Google OAuth Phase 2 — Environment

ตั้งค่า env บน Elastic Beanstalk/server: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (ถ้าใช้ Web OAuth client แบบ confidential), `GOOGLE_CALLBACK_URL` (ต้องตรงกับ Google OAuth redirect URI), `GOOGLE_SCOPES` (ค่าเริ่มต้น `openid profile email`) และ `AUTH_STATE_SECRET` เป็น random secret คงที่ยาวๆ

Google Login ติดต่อ `https://accounts.google.com/o/oauth2/v2/auth` โดยตรง และ callback ของเกมแลก authorization code ที่ `https://oauth2.googleapis.com/token`; ไม่มี Cognito อยู่ในเส้นทาง Google Login นี้

Authorized JavaScript origins ให้เป็น origin HTTPS ของเกม และ Authorized redirect URI ให้เป็น `https://<game-domain>/auth/google/callback` แบบตรงตัว

Scopes เริ่มต้นคือ `openid profile email` และโค้ดตรวจลายเซ็น/issuer/audience/expiry/nonce ของ Google ID token ฝั่ง server ก่อนยอมรับ Google identity; ห้ามเอา Google access/refresh token มาเก็บใน localStorage

## Diagnostics Center (v10)

หน้า `admin.html` มีแท็บ **🩺 ปัญหา / บั๊ก** สำหรับดูข้อผิดพลาดจาก `index`, `host`, `player`, JavaScript, Socket.IO, HTTP และ server-side logs

ระบบ client diagnostics ใช้ `public/js/error-reporter.js` แยกจาก game logic และส่งข้อมูลไปยัง `/api/diagnostics/client-error` แบบไม่บล็อกหน้าเกม

ศูนย์ Admin จะแยกให้เห็น:
- Error ล่าสุด พร้อมหน้า/ไฟล์/บรรทัด/stack
- HTTP และ Socket errors
- AWS `AccessDenied` พร้อม action เช่น `dynamodb:BatchWriteItem` และ resource ARN ที่ถูกปฏิเสธ
- รายการ IAM permissions ที่เกมใช้ เพื่อดูว่า role ควรมี action ใด

Diagnostics เก็บไว้ใน memory ของ process สูงสุด 500 รายการ และถูกล้างเมื่อ server process restart/deploy หรือเมื่อ Admin กด **ล้างบันทึก**

การแจ้งเตือนทั่วไปในหน้าเกมใช้ CSS toast ผ่าน `wwToast/wwAlert` แทน browser `alert()` และกล่องยืนยันใช้ CSS modal เพื่อไม่บล็อก JavaScript event loop แบบ native dialog


### Legacy → Game Account migration

หน้า Admin มีปุ่ม **ย้ายเข้า Account** สำหรับข้อมูลผู้เล่น legacy เดิม โดยต้องระบุ `accountId` ปลายทางเอง ระบบจะย้าย TOTAL/ROLE และ EVENT อย่างเป็น idempotent, ใช้ marker `MIGRATION#LEGACY#...` ป้องกันย้ายซ้ำ และรองรับการ resume หากคัดลอก event ไม่ครบในครั้งแรก

## Diagnostics Share v3 + Cross-Log Causal Graph / Recursive Trace Links

- หน้า Admin สามารถสร้างลิงก์วินิจฉัยแบบ public, unguessable และมีอายุจำกัดจากเหตุการณ์เดียวได้ โดยปุ่ม **คัดลอกลิงก์ AI** จะคัดลอก URL ที่ AI/เบราว์เซอร์ที่เข้าถึงเว็บได้สามารถเปิดอ่านได้ โดยไม่ต้องล็อกอิน
- รายงานถูกเก็บใน DynamoDB partition เฉพาะ และใช้ token แบบสุ่มเป็น bearer capability; ค่าเริ่มต้นหมดอายุใน 3 วัน (`DIAGNOSTIC_SHARE_TTL_MS`) จำกัดสูงสุด 7 วัน/ต่ำสุด 15 นาที เพื่อให้ข้าม instance ของ Elastic Beanstalk ได้
- Human-readable: `/diagnostics/share/<token>` และ machine-readable: `/diagnostics/share/<token>.json`; หน้า HTML เป็น server-rendered `<pre>` ไม่มี JavaScript ที่ต้องรันก่อนอ่าน และมี `noindex`, `no-referrer`, `no-store`
- สามารถกำหนด host ที่ใช้สร้าง URL ด้วย `DIAGNOSTIC_PUBLIC_BASE_URL` เมื่อ deployment อยู่หลัง proxy/CDN ที่ต้องการ URL canonical เฉพาะ
- การวิเคราะห์ไม่ได้หยุดที่ข้อความ Error: ระบบผูก `traceId`, `sessionId`, `operationId`, `requestId`, `clientRequestId`, room และ event name แล้วสร้าง **first failure → blocking event → causal chain → downstream effects → next step** ตามหลักฐานที่มีจริง
- Socket.IO handler เก็บ payload ที่ sanitize แล้วและ `authObservation` แบบไม่เก็บ credential จริง เพื่อแยกกรณี **client บอกว่ามี tester pass** ออกจาก **server ได้รับ/ตรวจ/ให้สิทธิ์ tester pass จริงหรือไม่**
- รายงานยังเก็บ `authEvidence` ฝั่ง client → server และ `evidenceItemCount` เพื่อให้ AI อ่านจุดที่ credential/authorization แตกต่างกันได้โดยไม่ต้องไล่ log หลายชั้นเอง
- ตัววิเคราะห์รองรับ success ACK แบบ array สำหรับ `list_open_rooms`/`list_open_rooms_players` จึงไม่ตีความผลสำเร็จของ API รูปแบบเก่าเป็น error
- สำเนา public จะตัด token/secret/password/authorization/cookie, Google subject, email และ network identity บางชนิด รวมถึง mask AWS account ID ใน ARN และล้าง credential ที่หลุดอยู่ใน free-form message/stack
- ลิงก์เป็น bearer link: ผู้ถือ URL สามารถอ่าน snapshot ได้จนหมดอายุ จึงควรแชร์เฉพาะช่องทางที่เหมาะสมและไม่ฝัง report ไว้ใน query string
- v3 เพิ่ม **Cross-Log Causal Graph**: รายงานจะระบุว่า log นี้มี upstream cause กี่ตัว, downstream effect กี่ตัว และ log ใดเป็นเพียง correlation ที่ยังไม่ฟันธงเหตุ→ผล
- ทุก causal edge มี `relation`, `confidence`, `score`, `timeDeltaMs` และ `reasons` เพื่อให้ AI แยก “หลักฐานเชิงเหตุ→ผล” ออกจาก “เกิดใกล้กันเฉย ๆ” ได้
- ในรายงานจะมี `REPORT URL` / `JSON URL` ของ event ที่เกี่ยวข้อง โดยเปิด `/diagnostics/share/<token>/event/<eventId>` เพื่อโฟกัส log นั้น และจากรายงานนั้นสามารถไล่ upstream/downstream ต่อได้อีก
- ระบบสร้าง graph จาก correlation หลายระดับ (operation/request/trace/session/room) + semantic event transition + เวลา จึงรองรับกรณี root cause กับ symptom คนละชนิดของ log แต่ยังอยู่ใน incident เดียวกัน
- `nodeReports` เก็บ summary ของ node สำคัญ เพื่อให้เปิด log ตัวถัดไปแล้วเห็น root cause/impact ของ node นั้นโดยไม่ต้องเดาเองจากข้อความ raw
- รายงานยังระบุชัดว่าเป็น **incident snapshot ณ เวลาที่สร้างลิงก์**; log ที่เกิดหลังจาก snapshot จะไม่โผล่ในลิงก์เดิมจนกว่าจะสร้าง snapshot ใหม่
